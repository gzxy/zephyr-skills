# 代码审查模式

审查当前本地 Feature 分支相对 `origin/test` 的已提交变更，以及工作区、暂存区和未跟踪文件，不修改代码。

1. 在仓库中查找 `BUGBOT.md`：先检查仓库根目录，再检查相关包目录。若文件存在，读取并应用其中针对该仓库的审查标准；与下方默认标准冲突时，以仓库说明为准。
2. 确认当前本地分支匹配 `feature/**/<纯数字需求ID>`；不匹配时停止并请用户切换或指定正确的 Feature 分支。执行 `git fetch origin test` 并确认 `origin/test` 存在，然后以 `git merge-base HEAD origin/test` 为共同祖先，审查 `origin/test...HEAD` 的已提交变更以及 `origin/test..HEAD` 范围内的普通提交。不要用双点文件 diff 代替 merge-base 范围，以免把 test 分支后续提交混入审查结果。
3. 同时审查当前工作区全部未提交变化：`git diff` 的未暂存变更、`git diff --cached` 的暂存变更，以及 `git status --short` 显示的未跟踪文件内容。合并重复内容后统一报告，并明确区分已提交、暂存、未暂存和未跟踪范围。
4. 阅读上述 diff 以及足够的上下文代码，验证每个问题。必要且安全时运行聚焦的只读检查或测试。
5. 优先报告缺陷，不把个人代码风格偏好当作问题。检查逻辑与边界条件、安全与权限边界、并发与执行顺序、错误处理与资源清理、数据丢失、兼容性，以及行为变更缺少测试等情况。
6. 只报告有证据且可采取行动的问题。每个问题包含严重程度、文件和行号、影响、触发条件与简洁的修复方向。如果上下文代码能证明 diff 没有问题，不要仅凭局部差异声称存在缺陷。

使用以下严重程度：

- **P0：** 会立即造成大范围故障、严重数据丢失或关键漏洞。
- **P1：** 很可能影响生产环境或阻塞发布的高影响缺陷。
- **P2：** 影响范围较窄但真实存在的缺陷，或有明显回归风险。
- **P3：** 值得修复的低影响正确性或可维护性问题。

如果没有可采取行动的问题，明确说明“未发现问题”，并注明审查覆盖范围和未验证区域。问题列表后保留一段简短的剩余风险或测试缺口说明。
